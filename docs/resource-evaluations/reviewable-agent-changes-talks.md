# Three talks on reviewing agent-written changes (Litt, Gupta, Lopopolo)

**Reviewed**: 2026-11-08. **Scores**: Litt 4/5, Gupta 3/5, Lopopolo 3/5. Target: the planned workflow page on reviewable agent changes; nothing is integrated by this evaluation alone. Related: [Resisting Cognitive Surrender](knlb-cognitive-surrender.md), [#077 Comprehension debt](077-comprehension-debt-ai-coding.md).

The three talks answer one question from different positions: how does a human reviewer keep understanding code that an agent wrote? None of them reports a controlled measurement of review quality. All quotes below were read in the published captions on 2026-11-08; caption errors are left as transcribed.

## Litt: an explainer the author must pass before asking for review (4/5)

- [84 s](https://www.youtube.com/watch?v=WkBPX-oDMnA&t=84): "there are lots of ways to understand. Be, you know, the days of just reading code line by line and that's not the only way anymore."
- [480 s](https://www.youtube.com/watch?v=WkBPX-oDMnA&t=480): the speaker's `explainedif` skill produces a code explainer document. "We start with background. We do not start with what happened in this change." Then intuition before details: "You can think of this sort of as like a well-written commit message, a little deeper."
- [577 s](https://www.youtube.com/watch?v=WkBPX-oDMnA&t=577): "literate code diffs. Give me prose. Explain it to me in the right order. Tell me before each file what's going on."
- [663 s](https://www.youtube.com/watch?v=WkBPX-oDMnA&t=663): a five-question quiz at the bottom of the explainer. "my rule is I don't send code to uh others on my team to review unless I can pass the quiz about what my agents wrote."

**What it adds**: a concrete document structure (background, intuition, interactive figures where useful, ordered prose per file, quiz) and a gate on the author, not the reviewer. **Limit**: one demonstration on a video game project; "shocking the number of times this has caught me" is a self-report without a count. Litt warns that interactivity "can just be a crutch, and it can be kind of slop".

## Gupta: review debt and the "why, not what" criterion (3/5)

- [288 s](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=288): "Review debt. It's the accumulating gap between code your agent has produced and the code humans have actually reviewed, trusted, and understood."
- [684 s](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=684): "Does the PR explain the why or just the what?" A low-gap example body carries "the symptom, the diagnosis, the change, and the link to the benchmark".
- [636 s](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=636): textual attribution signals (co-authored footer, branch prefixes, "generated by" phrases) checked on "three public repos, which comprised of 524 PRs". The highest signal was the co-authored footer; on repo C, the lowest-scoring signal "was 0% on the repo C. Even though it was done by coding agent", and the speaker adds that the repository "might have blocked it". Which signal scored 0% is not stated, and agent authorship is the speaker's statement.

**Second-hand figures, not verified**: at [83 s](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=83) the speaker cites a Faros AI 2026 benchmark (median PR review time up 441.5%, 31% more PRs merged with no review) and derives that reviewed PRs take 5.4 times longer ("if you calculate"); at [136 s](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=136) 16% more PRs per developer comes from "the Faros AI acceleration Whiplash benchmark" of April 2026. Neither report was opened for this evaluation; do not reuse these numbers without reading them.

**What it adds**: a competing term for comprehension debt, a usable criterion for PR descriptions, and a speaker-reported case where one textual attribution signal scored 0% on a repository that may have suppressed such markers. **Limit**: the scoring weights are the speaker's; the 524-PR check uses unnamed repositories and cannot be reproduced.

## Lopopolo: let the agent defer or push back on review feedback (3/5)

- [972 s](https://www.youtube.com/watch?v=CeOXx-XTYek&t=972): "on the code authoring agent side, we also gave it the flexibility to either defer or push back against review feedback". A comment that "could blow up the scope by a factor of two" is "more of an FYI, right? File it to the backlog". "without the context that this is permissible, the coding agents are going to bias toward what they do, which is following instructions."
- [947 s](https://www.youtube.com/watch?v=CeOXx-XTYek&t=947): "the reviewer agents were instructed to bias toward merging the thing, to not surface anything greater than a P2 in priority", added because author and reviewer agents were "not converging".

**What it adds**: a case for typing review feedback, so that an agent can tell a question or an aside from a required change. **Limit**: an environment where agents review and merge autonomously; "P2" was not formally defined ("We didn't really define P2"), but the agents were given "a framework within which to uh score its output", with P0 the worst. It does not transfer as is to human-reviewed merge requests.

## Not verified here

- Any effect of these practices on defects found, review time or understanding. No talk measures one.
- The Faros AI figures and the identity of Gupta's three repositories.
- Whether the `explainedif` skill is published.

## Decision

Use the three talks as attributed practice in the planned page: Litt for the explainer structure and the author-side quiz gate, Gupta for the "why, not what" description criterion and the limits of trailer-based attribution, Lopopolo for typed feedback with explicit permission to defer. State each as one team's practice, and keep the Faros figures out of the guide until the report is read.
